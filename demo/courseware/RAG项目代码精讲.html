二、离线导入链路（代码走读）

2.1 MinerU 深度解析 核心结论

一句话 PDF 本质是排版格式，直接抽文本会结构坍塌；MinerU 能把 PDF 还原成带标题层级、表格、公式的 Markdown。

前端类比 就像把一个设计稿（Figma/PDF）还原成带语义的 HTML——不是截一张图，而是识别出"这是 H1 标题""这是表格""这是列表"。

代码路径 app/import_process/agent/nodes/node_pdf_to_md.py

# 核心逻辑：调用 MinerU 把 PDF 转成结构化 Markdown
from magic_pdf.pipe.UNIPipe import UNIPipe
# 输出：带 # ## ### 标题层级的干净 Markdown
# 后续切片就是基于这个 Markdown 的标题边界

反例：如果直接用 PyPDF2 抽文本，标题和正文混在一起，切片时不知道哪里是哪里，检索出来的证据上下文断裂。

2.2 语义切片（Semantic Chunking） 核心结论

一句话 按章节/段落边界切，不按固定字数切；每个 chunk 继承父级标题路径，15% overlap 保证上下文不丢。

前端类比 就像 React 组件的懒加载边界——不是随便从中间切断，而是在语义完整的边界（组件/章节）切。overlap 就像虚拟滚动的预加载，保证滚动时上下文连续。

代码路径 app/import_process/agent/nodes/node_document_split.py

# 切片策略：
# 1. 按标题 (# / ## / ###) 维护标题栈，每个 chunk 记录 breadcrumb
# 2. 超长 section 按句子二次切分
# 3. chunk 之间保留 15% 重叠区域
# 示例 breadcrumb: "RAG系统 / 多路召回引擎 / 混合向量检索"

为什么是 15%？ 太小（5%）上下文断了，太大（30%）冗余重复。15% 是经验值。

2.3 BGE-M3 双路向量 核心结论

一句话 每个 chunk 一次输出两种向量：dense（语义向量）+ sparse（关键词向量），分别入库。

向量类型作用前端类比
Dense语义泛化，"懂意思"像搜索的"你是不是想找…"联想
Sparse精确匹配，"查得准"像 Ctrl+F 关键词搜索

代码路径 app/lm/embedding_utils.py

# 一次调用输出两种向量
from FlagEmbedding import BGEM3FlagModel
model = BGEM3FlagModel('BAAI/bge-m3', use_fp16=True)
output = model.encode(text)
dense_vec = output['dense_vecs']      # 1024 维稠密向量
sparse_vec = output['lexical_weights'] # 稀疏关键词权重

为什么要两种？ 单靠 dense：用户搜"HAK 180 烫金机"可能召回"热转印设备"（语义相近但不是同一个）；单靠 sparse：用户搜"怎么开机"召回不到"启动电源"（用词不同但意思一样）。

2.4 Milvus 混合向量检索 核心结论

一句话 Dense 和 Sparse 两路并行检索，结果加权融合（dense 0.8 + sparse 0.2）。

前端类比 就像搜索引擎同时跑 BM25 和向量召回，最后用 RRF 或加权融合排序。

代码路径 app/clients/milvus_utils.py

# 混合搜索请求：同时发 dense 和 sparse 两路
reqs = create_hybrid_search_requests(
    dense_vector=dense_vec,
    sparse_vector=sparse_vec,

三、在线查询链路（核心）

3.1 LangGraph 状态机编排 核心结论

一句话 用 LangGraph 把查询流程做成状态机，支持条件分叉、并行节点、状态流转。

前端类比 就像 React Router + 状态机：每个节点是一个页面/组件，state 是全局状态，条件边就是路由守卫（有 answer 就跳结果页，没有就继续走检索）。

3.2 商品名智能确认（多规则） 核心结论

一句话 用户说"这个多少钱"，系统先用 LLM 提取商品名，再去 Milvus 对齐，分 A/B/C/D 四种情况处理。

规则条件处理方式
A只有一个高置信度（>0.85）直接确认，继续检索
B多个高置信度优先精确匹配，否则取最高分
C只有中置信度（0.6~0.85）生成反问句，让用户选
D全部 < 0.6直接拒绝，说没找到

四、多路召回（核心亮点）

4.1 为什么要多路召回？ 核心结论

一句话 单路检索有盲区：向量懂语义但不懂精确术语，BM25 反过来。多路并行 + 融合，召回率比单路高 20%+。

前端类比 就像搜索时同时跑"语义搜索"和"关键词搜索"，结果合并后排序——不会因为用户换了个说法就搜不到。

4.2 HyDE（Hypothetical Document Embeddings） 核心结论

一句话 用户 query 通常很短（"多少钱？"），直接向量检索效果差。先让 LLM 根据问题"假设性"写一段答案，再拿这段答案去向量检索——因为答案和文档的语义分布更接近。

前端类比 就像搜索时你先脑补"我要找的应该是关于 XX 的内容"，再带着这个脑补去搜——比直接搜两个字准多了。

# HyDE 流程：
# 1. 用户问："HAK 180 多少钱？"
# 2. LLM 生成假设答案："HAK 180 烫金机的市场价格约为 5000 元左右，根据配置不同有所浮动..."
# 3. 用这段假设答案去向量检索（而不是用原始 query）
# 4. 召回率显著提升
4.3 RRF 倒数排名融合 核心结论

一句话 多路召回的结果不看分数，只看排名，用公式 score = Σ 1/(k + rank) 融合，k=60。

前端类比 就像多个评委打分——各路的分数量纲不一样（cosine 是 0~1，BM25 可能几十），直接加权求和会被某一路"分数劫持"。RRF 只看排名第几，公平且简单。

代码路径 app/query_process/agent/nodes/node_rrf.py

def reciprocal_rank_fusion(source_weights, k=60):
    score_map = {}
    for docs, weight in source_weights:
        for rank, item in enumerate(docs, start=1):
            chunk_id = item.get("chunk_id")
            score_map[chunk_id] = score_map.get(chunk_id, 0) + weight * (1.0 / (k + rank))
    # 按分数降序返回
    return sorted(score_map.items(), key=lambda x: -x[1])

为什么不用归一化加权？ 各路分数分布差异大，归一化很难调；RRF 不需要调参，鲁棒性极强，工业标配。

五、Rerank 精排（决定答案上限）

5.1 Rerank 和召回的本质区别 核心结论
召回（Recall）重排（Rerank）
目标求全，不漏求准，挑最好的
模型双塔（query 和 doc 分别编码）交叉编码（query+doc 拼一起）
速度快（毫秒级，百万级扫）慢（只对几百条候选算）
精度粗精

前端类比 召回就像搜索的"初步结果列表"，Rerank 就像你逐一点开看哪个最相关——后者慢但准。

5.2 动态 TopK 断崖截断 核心结论

一句话 不是机械取前 10 条，而是检测分数断崖：如果第 i 条和第 i+1 条的分数差超过阈值（绝对 0.5 或相对 25%），就截断。

代码路径 app/query_process/agent/nodes/node_rerank.py

# 断崖截断逻辑：
for i in range(min_topk - 1, max_topk - 1):
    gap = score[i] - score[i+1]
    rel = gap / abs(score[i])
    if gap >= 0.5 or rel >= 0.25:  # 触发断崖
        topk = i + 1  # 截断到这里
        break

为什么要这么做？ 避免把低相关的噪声文档送进 LLM——上下文越长，LLM 越容易被干扰，答案质量越差。

六、面试速查表

Q1：召回和检索是一个意思吗？
不是。召回是检索的第一阶段（粗排），追求"别漏掉"；检索 = 召回 + 重排（Rerank）。召回从百万级文档粗筛出几百条，Rerank 再精挑出 top 3~5 条。
Q2：为什么用 RRF 不用加权求和？
各路分数量纲不一样（cosine 0~1，BM25 可能几十），归一化做不好就会"分数劫持"。RRF 只看排名不看分数，简单且鲁棒，是工业标配。
Q3：HyDE 是什么？为什么有用？
用户 query 通常很短、语义稀疏，直接向量检索效果差。先让 LLM 假设性写一段答案，再拿这段答案去检索——因为答案和文档的语义分布更接近，召回率更高。
Q4：切片为什么要 overlap？多少合适？
保证跨 chunk 的上下文不被切断。太小（5%）上下文断了，太大（30%）冗余重复。15% 是经验值，平衡连贯性和检索精度。
Q5：为什么用 LangGraph 不用普通顺序调用？
查询链路有条件分叉——商品名确认完可能直接返回（反问/拒绝），也可能走 4 路并发。LangGraph 天然支持状态机、条件边、并行节点，比自己写 if-else 可维护性强太多。
Q6：Dense 和 Sparse 向量分别解决什么问题？
Dense 懂语义泛化（"怎么开机" → "启动电源"），Sparse 懂精确术语（型号、编号）。混合检索兼顾两者，dense 权重 0.8，sparse 权重 0.2。
Q7：Rerank 的动态 TopK 是什么意思？
不是固定取前 N 条，而是检测分数断崖——相邻两条分数差超过绝对阈值 0.5 或相对阈值 25% 就截断。避免低相关噪声进 LLM，提升答案质量。
