3. 概念讲解

概念 A · RAG（检索增强生成）

一句话结论RAG = 先检索相关资料，再把资料塞进 Prompt，让大模型基于资料回答，从而减少幻觉、答案可溯源。 [通用知识]
大白话以前问大模型问题，它只能靠「背过的知识」回答，超出训练范围就瞎编。RAG 相当于在它回答前先给它一本「指定参考书」，告诉它：只许照着这本书答。
前端类比普通 LLM 像没有状态管理的组件，RAG 像给它挂了一个「缓存 + 数据层」：先查数据再渲染。或者类比搜索引擎：你不是直接让 AI 凭记忆写，而是「搜索 → 拿到网页 → 让 AI 读网页后总结」。
项目代码导入链路把知识写进 Milvus（app/import_process/agent/main_graph.py），检索链路先从 Milvus 取回资料再交给 LLM（app/query_process/agent/main_graph.py）。
最小代码
# 检索链路的最后一环：把检索结果拼进 Prompt 再问 LLM
prompt = load_prompt("answer_out", context=context_str,
                     history=history_str, item_names=item_names_str,
                     question=question)
answer = llm.invoke(prompt)  # LLM 只基于 context 作答
为什么这样写：把「检索」（context）和「生成」（answer）解耦，检索质量提升时生成质量自动提升。
反例不用 RAG：让 LLM 直接回答「HAK 180 烫金机怎么操作」，模型没学过这个型号，会编造操作步骤 —— 就是幻觉。
并发场景a、b、c 三个用户同时问不同商品：每个请求独立走自己的检索链路，状态（QueryGraphState）按 session_id 隔离，互不污染。这是 LangGraph 每请求一个 state 实例保证的。
边界RAG 不是万能的：如果知识库本身没资料（如全新未导入的产品），检索返回空，答案质量取决于 LLM 的兜底 prompt；如果切片质量差，检索结果再准也答不好 —— RAG 的天花板是「检索质量 × 生成质量」。
验证方法打开导入主图注释、检索主图注释，数一数每个链路有几个节点；或直接问项目一个库里没有的问题，观察回答是否老实承认不知道。
30 秒面试「RAG 是检索增强生成：先通过向量检索从知识库里取回和问题相关的文档，再把这些文档作为参考内容拼进 Prompt，让大模型基于它们生成答案。它能解决大模型幻觉和知识时效问题。我们项目里导入链路负责把文档切片、向量化存进 Milvus，检索链路负责召回、排序、生成。」

概念 B · 掌柜智库项目架构（双链路）

一句话结论项目拆成「知识库构建（导入）」与「智能问答（检索）」两条 LangGraph 工作流，中间用 Milvus 向量库连接。 [项目事实]
大白话导入链路像「出版社编辑流程」：把 PDF/MD 文档拆成小块、给每块生成向量指纹、存进数据库。检索链路像「客服接待」：听懂问题 → 去库里找最相关的几块资料 → 组织成答案回复。
前端类比导入 = 构建期（build）：源码 → 转译 → 分包 → 产出静态资源（assets）。检索 = 运行期（runtime）：路由 → 数据请求 → 渲染 → 响应。两条链路完全解耦，就像 CI/CD 构建和线上服务是两个独立系统。
项目代码导入主图：app/import_process/agent/main_graph.py；检索主图：app/query_process/agent/main_graph.py；状态：app/import_process/agent/state.py 与 app/query_process/agent/state.py。
最小代码
# 检索主图（节选）——可见「分叉 + 合并」的多路召回结构
builder.add_node("node_multi_search", lambda x: x)  # 虚拟分叉点
builder.add_node("node_search_embedding", node_search_embedding)
builder.add_node("node_web_search_mcp", node_web_search_mcp)
builder.add_node("node_join", lambda x: {})          # 虚拟合并点
builder.add_edge("node_multi_search", "node_search_embedding")
builder.add_edge("node_multi_search", "node_web_search_mcp")
builder.add_edge("node_search_embedding", "node_join")
builder.add_edge("node_web_search_mcp", "node_join")
为什么这样写：虚拟节点只做「分叉/合并中转」，无业务逻辑，让四路搜索并行执行再统一汇合。
反例如果只有检索链路没有导入链路：库里永远是空的，检索永远空手而归。两条链路缺一不可。
并发场景一个用户在导入 10 个 PDF 的同时，另一个用户在检索提问：两者各走各的主图、各用各的 session_id/task_id，互不干扰；导入结果写入 Milvus 后，检索链路立即可用（读写分离的自然效果）。
边界导入和检索共用同一套 Milvus 集合时，导入中（数据未完全写入）检索可能读到半成品 —— 项目用 task 状态（running/done）标记导入进度，前端据此提示「导入中，稍后再试」。
验证方法分别打开两个 main_graph.py，用「数节点」的方式核对：导入 7 个业务节点、检索 8 个节点（含 2 个虚拟节点）。
30 秒面试「掌柜智库是一个企业级私有知识库问答系统。它分两条链路：导入链路把 PDF/MD 文档切片、向量化存入 Milvus；检索链路对用户问题做意图确认、多路召回、RRF 融合、Rerank 重排，最后基于检索结果生成答案。两个链路都用 LangGraph 编排，中间靠向量库衔接。」

概念 C · 技术栈选型（每个组件解决什么问题）

一句话结论LangGraph 编排流程、Milvus 存向量、MinIO 存文件、MongoDB 存历史、FastAPI+SSE 做实时输出 —— 每个组件都有不可替代的职责。 [项目事实]
大白话想象一条流水线：LangGraph 是「流水线总控」；Milvus 是「按指纹找资料的仓库」；MinIO 是「放原始图片的网盘」；MongoDB 是「记录每次对话的账本」；SSE 是「让前端像看直播一样看到答案逐字出现」的通道。
前端类比
组件前端类比职责
LangGraph路由 + 状态管理 + 中间件编排节点、传递状态、条件分支
Milvus带索引的数据库向量近似检索（TopK）
MinIOCDN / 对象存储存 PDF 转出的图片，供前端展示
MongoDBlocalStorage / 后端 DB历史对话、消息、item_names
FastAPI+SSEEventSource / WebSocket 推送流式输出答案增量
uvpnpm / npmPython 依赖与虚拟环境管理
项目代码配置类集中在 app/conf/：milvus_config.py、minio_config.py、reranker_config.py、lm_config.py、mineru_config.py、embedding_config.py、bailian_mcp_config.py。
最小代码
# reranker_config.py：环境变量 → 配置对象（dataclass）
@dataclass
class RerankerConfig:
    bge_reranker_large: str
    bge_reranker_device: str
    bge_reranker_fp16: bool

reranker_config = RerankerConfig(
    bge_reranker_large=os.getenv("BGE_RERANKER_LARGE"),
    bge_reranker_device=os.getenv("BGE_RERANKER_DEVICE"),
    bge_reranker_fp16=os.getenv("BGE_RERANKER_FP16") in ("1", "True", "true", 1))
为什么这样写：所有外部依赖的地址/路径集中从 .env 读取，换环境（开发/生产）只改配置不改代码。
反例如果不用向量数据库而用普通数据库：无法做「语义相似度」检索，只能精确匹配关键词，「万用表怎么用」和「如何操作万用表」就匹配不上了。
并发场景同时 10 个请求流式生成：SSE 按 session_id 分通道推送（push_to_session），每个前端连接只收到自己会话的增量，不会串台。
边界技术栈不是越全越好：小规模场景 SQLite + 关键词搜索也能做 RAG；这里选 Milvus/SSE 是因为目标是对接前端实时问答、支持并发和企业级数据量。
验证方法看 pyproject.toml 与 uv.lock 中的依赖清单，对照上述组件逐一找到。
30 秒面试「技术栈选型按职责分工：LangGraph 做流程编排和状态管理；BGE-M3 做稠密+稀疏双路向量；Milvus 做向量检索；MinIO 存图片文件；MongoDB 存对话历史；FastAPI + SSE 给前端做流式输出。选型原则是每个组件解决一个明确问题，且都是各自领域的主流方案。」

闭卷回答（先自己答，再看课件）

  1. RAG 与直接问大模型的核心区别是什么？

动手任务：画出并核对双链路

  • 输入：项目根目录 app/import_process/agent/main_graph.py 与 app/query_process/agent/main_graph.py
  • 操作：① 数出导入链路业务节点数量（应为 7）；② 数出检索链路节点数量（应为 8，含 2 个虚拟节点）；③ 找出检索链路里「条件路由」函数名（应为 route_after_item_confirm）
  • 预期结果：能不看课件，在纸上画出两条链路的完整节点顺序
  • 失败先查：如果节点数量对不上，检查是否把虚拟节点（lambda x: x / lambda x: {}）漏数了
