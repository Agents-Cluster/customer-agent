3. 概念讲解

概念 A · TypedDict 状态类（State）

一句话结论状态类是一个「字段清单」，规定工作流里所有节点共享的数据结构和类型。 [项目事实]
大白话把工作流想象成一辆接力车：每个节点往车里放东西、取东西。TypedDict 就是这张「货物清单」，写明了车里该有哪些东西、各是什么类型，防止节点之间乱塞。
前端类比类似 TypeScript 的 interface + Redux 的单一状态树。前端里你定义 `type AppState = { user: User; cart: Cart[] }`，LangGraph 里就是 `class QueryGraphState(TypedDict)`，IDE 有自动补全、写错字段直接报错。
项目代码app/query_process/agent/state.py 定义 QueryGraphState：session_id、original_query、embedding_chunks、hyde_embedding_chunks、web_search_docs、rrf_chunks、reranked_docs、prompt、answer、item_names、rewritten_query、history、is_stream。
最小代码
from typing_extensions import TypedDict
class QueryGraphState(TypedDict):
    session_id: str          # 会话唯一标识
    original_query: str      # 用户原始问题
    reranked_docs: list      # 重排后的最终 Top-K 文档
    answer: str              # 最终生成的答案
    is_stream: bool          # 是否流式输出
为什么这样写：TypedDict 让每个节点 `state.get("reranked_docs")` 都有类型提示，团队协作不易写错字段名。
反例如果不用 TypedDict 而用普通 dict：节点间传参全靠记忆，一个拼写错误（reranked_doc 少个 s）会在运行时静默失败，非常难排查。
并发场景a、b、c 三个会话同时运行：LangGraph 每次 invoke 创建独立的状态实例，同一份 TypedDict 定义被三个实例复用，互不干扰 —— 就像 Redux 里 createStore 多次实例化。
边界TypedDict 只是「类型约定」，运行时并不强制校验字段是否齐全。节点里仍要写 `state.get("xxx") or []` 这类防御性取值，防止字段缺失崩溃。
验证方法打开 state.py 看字段注释；在编辑器里输入 `state.` 观察是否出现字段补全。
30 秒面试「LangGraph 用 TypedDict 定义工作流状态，相当于给所有节点一张共享数据结构的类型清单。节点函数接收这个状态、返回部分字段的更新，LangGraph 自动合并，实现节点间数据传递，同时享受 IDE 类型检查。」

概念 B · 节点、边与入口（add_node / add_edge / set_entry_point）

一句话结论节点 = 一个业务函数；边 = 执行顺序；入口 = 第一个执行的节点。 [项目事实]
大白话节点是「干活的工人」，边是「工人之间的传送带」，入口是「第一个上班的工人」。LangGraph 负责按传送带顺序把状态传给每个工人。
前端类比像 express/koa 中间件栈：每个中间件（节点）处理请求对象（state），调用 next() 进入下一个。也像 webpack 的 loader 链：entry → loader1 → loader2 → output。
项目代码app/import_process/agent/main_graph.py：add_node 注册 7 个节点，set_entry_point("node_entry")，然后一串 add_edge 串起流水线。
最小代码
workflow = StateGraph(ImportGraphState)
workflow.add_node("node_entry", node_entry)          # 注册节点（名字, 函数）
workflow.set_entry_point("node_entry")               # 指定入口
workflow.add_edge("node_bge_embedding", "node_import_milvus")  # 顺序边
kb_import_app = workflow.compile()                   # 编译为可执行对象
kb_import_app.invoke(initial_state)                  # 触发执行
为什么这样写：声明式描述流程，顺序/分支一目了然，比散落的 if-else 好维护。
反例不注册节点直接用函数调函数（node1 → node2 → node3）：流程藏在调用栈里，想插入一个节点、加个分支都要改多处代码；LangGraph 里只改 add_edge 一行。
并发场景一个导入任务执行到 node_bge_embedding 时，另一个任务可以同时跑在 node_document_split —— 节点函数本身是无共享状态的，LangGraph 支持多任务交错。
边界节点函数必须「接收 state、返回 dict（或 state）」—— 返回的 dict 会被合并进状态。如果节点函数不返回任何值，后续节点拿不到它的产出。
验证方法运行 node_entry.py 的单元测试（`python -m app.import_process.agent.nodes.node_entry`），观察三组测试的日志输出。
30 秒面试「LangGraph 里节点是普通函数，边定义执行顺序，入口指定第一个节点。我在导入链路注册了 7 个业务节点，用 add_edge 串成流水线，compile 后 invoke 执行。改流程时只改边，不动节点函数，可维护性好。」

概念 C · 条件路由（add_conditional_edges）

一句话结论条件路由 = 根据当前状态动态决定下一个节点，返回值可以是节点名或 END。 [项目事实]
大白话流水线上的「分拣员」：看一眼货（state）上的标签，把货送到不同的传送带。比如入口节点判断文件是 PDF 还是 MD，分拣员就把任务送到不同的处理线。
前端类比前端路由守卫（beforeEach）：根据登录态决定去 /login 还是 /home。或 Redux 中间件里根据 action.type 分发到不同 reducer。
项目代码app/import_process/agent/main_graph.py 的 route_after_entry：is_md_read_enabled → node_md_img；is_pdf_read_enabled → node_pdf_to_md；否则 END。检索主图的 route_after_item_confirm：state 有 answer 就直接去输出，否则去多路搜索。
最小代码
def route_after_entry(state: ImportGraphState) -> str:
    if state.get("is_md_read_enabled"):
        return "node_md_img"      # MD 直接读，跳过 PDF 转 MD
    elif state.get("is_pdf_read_enabled"):
        return "node_pdf_to_md"   # PDF 先转 MD
    else:
        return END                # 都没开，结束

workflow.add_conditional_edges("node_entry", route_after_entry,
    {"node_md_img": "node_md_img", "node_pdf_to_md": "node_pdf_to_md", END: END})
为什么这样写：把「判断逻辑」独立成函数，主图里只声明「入口节点走条件路由」，读代码时一眼看到分支结构。
反例不用条件路由，在 node_entry 内部直接调用下一个节点函数：分支逻辑和业务逻辑混在一起，而且 LangGraph 的图结构里看不到分支，调试时链路不清晰。
并发场景同时导入一个 PDF 和一个 MD：两个任务各自的状态里开关不同，分拣员各判各的，一个走 PDF 线、一个走 MD 线，互不影响。
边界路由函数的返回值必须与注册的节点名或 END 精确一致，否则 LangGraph 找不到目标节点直接报错。写错一个字符串是最常见的坑。
验证方法在 route_after_entry 里临时加一行 logger.info(state.get("is_md_read_enabled"))，跑导入任务看日志走向哪个分支。
30 秒面试「条件路由让工作流根据状态动态分支。导入链路里入口节点按文件类型路由到 PDF 或 MD 处理线；检索链路里如果意图确认阶段已经能直接回答（比如反问用户），就跳过检索直接输出。判断逻辑独立成函数，图结构清晰。」

概念 D · 虚拟节点：多路并发的分叉与合并

一句话结论虚拟节点（lambda 函数）只做「分叉 / 合并中转」，本身无业务逻辑，解决多分支流程的组织问题。 [项目事实]
大白话想象高速公路的分流岛和汇合口：分流岛不产生车流，只是让四辆车各走各的路；汇合口再把它们重新汇成一条路。node_multi_search 是分流岛，node_join 是汇合口。
前端类比类似 Promise.all 的语义：把 4 个请求（向量检索 / HyDE / Web搜索 / 图谱）同时发出去，等全部返回再统一处理。虚拟节点就是那个「同时发出」和「等全部返回」的编排点。
项目代码app/query_process/agent/main_graph.py：`builder.add_node("node_multi_search", lambda x: x)` 与 `builder.add_node("node_join", lambda x: {})`。四路搜索全部 add_edge 到 node_join。
最小代码
# 分叉：一个起点引出四条边
builder.add_edge("node_multi_search", "node_search_embedding")
builder.add_edge("node_multi_search", "node_search_embedding_hyde")
builder.add_edge("node_multi_search", "node_web_search_mcp")
builder.add_edge("node_multi_search", "node_query_kg")
# 合并：四条边汇入 node_join
builder.add_edge("node_search_embedding", "node_join")
builder.add_edge("node_search_embedding_hyde", "node_join")
builder.add_edge("node_web_search_mcp", "node_join")
builder.add_edge("node_query_kg", "node_join")
# node_join 之后统一进入排序
builder.add_edge("node_join", "node_rrf")
为什么这样写：`lambda x: x` 接收 state 原样返回（分叉点不修改）；`lambda x: {}` 返回空字典不更新状态（合并点只汇合）。要扩展第五路搜索，只需再加两条边。
反例把四路搜索串行（embedding → hyde → web → kg 一条链）：总耗时为四路之和；并行后总耗时 ≈ 最慢一路。在用户等待答案的场景，时延直接差 3-4 倍。
并发场景a 用户问烫金机、b 用户问万用表：各自四条搜索并行跑，各自 node_join 等待自己的四路结果，互不混流。
边界多路并行意味着可能某一路超时或失败（如 Web 搜索 MCP 挂了）：需要节点内部做好降级（返回空列表而不是抛异常），否则 node_join 等不到全部结果。项目里各检索节点均有 try/except 兜底。
验证方法读检索主图，数出「从 node_multi_search 出发有几条边」「汇入 node_join 有几条边」，应各为 4 条。
30 秒面试「检索主图用两个虚拟节点实现多路并发的分叉与合并：node_multi_search 把流程分到向量检索、HyDE、Web 搜索、知识图谱四路，node_join 等四路都返回后汇合，再统一进 RRF 排序。这样多路召回并行执行，时延接近最慢一路。」

概念 E · compile 与 invoke：从图到可执行应用

一句话结论compile() 把声明的图编译成可执行应用，invoke() 传入初始状态启动一次完整流程。 [项目事实]
大白话add_node/add_edge 是「画图纸」，compile 是「按图纸盖房子」，invoke 是「开门营业」。图纸可以反复盖房子，房子可以反复营业。
前端类比像 webpack 的 config（声明）→ build（编译）→ 运行产物。也像 Redux 的 createStore（一次创建，多次 dispatch）。
项目代码导入主图：`kb_import_app = workflow.compile()`；检索主图：`query_app = builder.compile()`。Web 服务里拿到编译好的 app 每次请求 invoke。
最小代码
# Web 服务端（检索）
query_app = builder.compile()
# 每次用户提问：
result_state = query_app.invoke({
    "session_id": sid, "original_query": question,
    "history": history, "is_stream": is_stream
})
answer = result_state.get("answer")
为什么这样写：compile 一次、invoke 多次，避免每次请求都重新建图；invoke 返回最终状态，取出 answer 即可。
反例每次请求都重新 add_node + compile：性能浪费，且图对象无法复用连接池等初始化资源。
并发场景同一个 query_app 被 10 个并发请求 invoke：LangGraph 为每次 invoke 建独立状态实例，应用对象本身线程安全可复用。
边界invoke 是同步阻塞的；本项目配合 SSE 流式输出时，节点内部用 push_to_session 推送增量，而不是等 invoke 全部结束才返回。
验证方法检索 Web 服务端（query_service.py）里找 query_app.invoke 的调用位置，看传入的初始 state 有哪些字段。
30 秒面试「LangGraph 的图先 compile 成可执行应用，启动时只编译一次；每次用户请求用 invoke 传入初始状态执行完整链路，返回最终状态。应用对象可复用、支持并发，和前端路由表一次注册多次分发是同一个思路。」

闭卷回答

  1. TypedDict 状态类相比普通 dict 的优势是什么？运行时它会强制校验吗？

动手任务：给导入链路加一条日志边

  • 输入：app/import_process/agent/main_graph.py
