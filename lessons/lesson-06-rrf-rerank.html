3. 概念讲解

概念 A · RRF：倒数排名融合

一句话结论RRF 把多路召回的排名按「倒数 + 权重」累加成统一分数，自动去重、重排，输出 TopN。 [项目事实]
大白话多路搜索结果谁更靠前、谁在更多路里出现，谁的分就高。像投票：每路按名次给分（第 1 名得票多、第 2 名少一点），再按各路权重加权，最后总票数排序。
前端类比像前端把多个接口的搜索结果「按来源排名合并」：每个接口给一份排序，前端用 RRF 算出综合排名 —— 不做复杂语义判断，纯排名运算。
项目代码app/query_process/agent/nodes/node_rrf.py：reciprocal_rank_fusion(source_weights, k=60, max_results=10)；输入 embedding_chunks + hyde_embedding_chunks（权重各 1.0），输出 rrf_chunks。
最小代码
for docs, weight in source_weights:          # 每路
    for rank, item in enumerate(docs, start=1):  # 排名从 1 开始
        chunk_id = item.get("chunk_id") or item.get("id")
        score_map[chunk_id] = score_map.get(chunk_id, 0.0) \
                              + weight * (1.0 / (k + rank))   # 核心公式
        chunk_map.setdefault(chunk_id, item)  # 去重：保留首次出现
merged.sort(key=lambda x: x[1], reverse=True)  # 按总分降序
merged = merged[:max_results]                  # 截断 Top10
为什么这样写：用 chunk_id 做跨来源匹配（同一切片出现在多路则累加），公式只依赖排名不依赖分数，无需训练。
反例不用 RRF 直接拼接：同一文档在向量路和 HyDE 路各出现一次，列表里重复两条；且无法体现「多路都认可」的文档更可信。
并发场景a、b 两个请求的 rrf 是各自 state 上独立计算，无共享可变状态，天然并发安全。
边界RRF 只看排名不看内容：两路都排名靠前的文档分高，但排名高≠真相关（比如某路整体检索质量差，靠前文档其实是垃圾）。所以 RRF 之后还需要模型级 Rerank 精读。
验证方法跑 node_rrf 的本地测试（mock embedding + hyde），打印融合前后数量，确认重复 chunk_id 被合并且 Top10 截断生效。
30 秒面试「RRF 是倒数排名融合：对每一路检索结果，按公式 score += weight * 1/(k+rank) 累加每个文档的得分，k=60 平滑排名影响。同一文档在多路都排名靠前，得分就高；用 chunk_id 去重，最后截断 Top10。它无需训练、只依赖排名，是融合阶段的轻量方案。」

概念 B · k 值的作用（超参数）

一句话结论k 是平滑系数：让排名对得分的影响更温和，避免第 1 名垄断总分、也让排名靠后的文档仍有贡献。 [通用知识]
大白话没有 k 时第 1 名得分是第 2 名的两倍，第一名的意见直接压过所有人；加了 k=60，第 1 名 ≈0.0164、第 2 名 ≈0.0162，差距小到必须「多路都认可」才能赢。
前端类比像评分系统里的「阻尼系数」：让极端分（全 5 星 vs 全 1 星）不要太悬殊；也像 CSS 的缓动函数，把陡峭曲线拉平。
项目代码app/query_process/agent/nodes/node_rrf.py：`reciprocal_rank_fusion(source_weights, k=60, max_results=10)`，k 为默认参数。
最小代码
# 直观对比（同一文档排第 1 和第 100 的得分差距）
# 无 k：1/1 = 1.0   vs  1/100 = 0.01   （差 100 倍）
# 有 k=60：1/61 ≈ 0.0164 vs 1/160 ≈ 0.00625（差 ~2.6 倍）
score = weight * (1.0 / (k + rank))
为什么这样写：k 越大排名差异越不敏感，越看重「被多少路召回」；k 越小排名越重要。60 是行业常用默认值。
反例k 设太小（如 k=1）：第 1 名 0.5、第 2 名 0.33，单路第 1 名主导，融合名存实亡。
并发场景k 是常量参数，无并发问题；多路并行检索完成后统一传入。
边界k 没有「最优解」，依赖数据集和任务；项目用 60 是经验默认值，需要 A/B 测试调优（属于 [待验证] 的可优化点）。
验证方法用同一组 mock 数据分别跑 k=1、k=60、k=200，对比最终排序差异，理解 k 的敏感性。
30 秒面试「k 是 RRF 的平滑超参数，默认 60。它让排名对分数的影响温和化：没有 k 时第一名得分是第二名的两倍、会垄断结果；加了 k 后前几名分数接近，必须多路都认可才能得高分，同时排名靠后的文档也保留合理贡献。」

概念 C · Rerank：模型精读打分

一句话结论Rerank 用专门的交叉编码模型（BGE-reranker-large）逐对精读「问题 × 文档」并打相关性分，弥补 RRF 只看排名的局限。 [项目事实]
大白话RRF 是「看名次算分」，Rerank 是「逐字读题再打分」。模型把问题和一个候选文档一起读，判断「这俩到底相关吗」，给出 0-1 之间的分。
前端类比像先按关键词粗筛（召回），再人工精读每篇判断是否采纳（精排）。对应前端「搜索结果 → 人工确认」的两段式漏斗。
项目代码app/query_process/agent/nodes/node_rerank.py；模型封装 app/lm/reranker_utils.py（FlagReranker 单例 get_reranker_model）；配置 app/conf/reranker_config.py；三个子步骤 step_1_merge_docs / step_2_rerank_docs / step_3_topk。
最小代码
# 问题与每个文档组成 (query, passage) 对，批量打分
question = state.get("rewritten_query") or state.get("original_query")
sentence_pairs = [[question, t] for t in texts]
scores = reranker.compute_score(sentence_pairs)   # 每对得一个分
scored_docs = [(doc, score) for doc, score in zip(doc_items, scores)]
scored_docs.sort(key=lambda x: x["score"], reverse=True)  # 降序精排
为什么这样写：交叉编码让模型同时看到问题和文档（而非各自独立编码），相关性判断更准。
反例只用 RRF 的排名结果直接送 LLM：RRF 排在前面但内容其实是无关的高频词文档，LLM 会被误导；Rerank 能把这种「排名高但真不相关」的文档筛下去。
并发场景Rerank 是模型推理，吃 CPU/GPU：候选多时逐个打分是串行批量；多个请求并发会争抢算力，所以候选数先被 RRF 截到 Top10，控制推理开销。
边界Rerank 模型打分无固定取值范围，只看相对大小排序；且模型可能对超长文本处理不稳定，所以打分前对文本做了标准化（text 字段优先 content/snippet）。模型推理失败时项目做了降级：返回原顺序、分数置 0，保证流程不断。
验证方法跑 node_rerank 本地测试（mock 含相关与无关文档），观察相关文档分数明显高于无关文档，Top1 符合预期。
30 秒面试「Rerank 用 BGE-reranker-large 交叉编码模型对『问题 × 候选文档』逐对精读打分。它和 RRF 的本质区别是：RRF 只看排名做轻量融合，Rerank 真正理解内容判断相关性。RRF 先融合去重到 Top10，Rerank 再精排筛掉『排名高但真不相关』的噪音，最后动态截断。」

概念 D · 动态 TopK：断崖截断

一句话结论不机械取前 N 条，而是检测相邻分数的「断崖落差」，落差过大就在断崖处截断，只保留质量明显高的那批。 [项目事实]
大白话分数 95、93、89、77、71 —— 前三名明显领先后两名（77 之后是断崖），就只取前三，别让 71 分这种「凑数文档」混进答案。
前端类比像「及格线动态划定」：不是固定 60 分及格，而是看分数分布，明显的分数断层就是及格线；也像价格锚点 / 聚类找拐点。
项目代码app/query_process/agent/nodes/node_rerank.py step_3_topk；常量 RERANK_MAX_TOPK=10、RERANK_MIN_TOPK=1、RERANK_GAP_RATIO=0.25、RERANK_GAP_ABS=0.5。
最小代码
max_topk = min(RERANK_MAX_TOPK, len(scored_docs))   # 上限 10
min_topk = RERANK_MIN_TOPK                          # 下限 1
topk = max_topk
# 从 min_topk 之后开始检测相邻分差（前 min_topk 强制保留）
for i in range(min_topk - 1, max_topk - 1):
    s1, s2 = scored_docs[i]["score"], scored_docs[i+1]["score"]
    gap = s1 - s2
    rel = gap / (abs(s1) + 1e-6)                    # 相对落差
    if gap >= RERANK_GAP_ABS or rel >= RERANK_GAP_RATIO:
        topk = i + 1                                # 断崖处截断
        break
topk_docs = scored_docs[:topk]
为什么这样写：同时用绝对阈值（0.5）和相对阈值（25%）判断「断崖」，避免固定 TopN 放低分文档进来；前 min_topk 强制保留防止空结果。
反例固定 Top5：第 5 名 71 分和第 4 名 77 分差距不大时还好，但若第 5 名是 30 分（断崖），固定 Top5 会把 30 分的垃圾文档送进 Prompt，污染答案。
并发场景TopK 计算是纯列表运算，无共享状态，并发安全。
边界断崖阈值是经验值（0.25/0.5），可能误判：分数整体都很接近时无断崖 → 取满 10 条；分数整体都很低时仍至少保留 1 条（min_topk）—— 兜底但不保证质量。属于 [待验证] 可调参数。
验证方法构造含断崖的 mock 分数（如 0.95/0.93/0.89/0.77/0.71），跑 step_3_topk 观察是否在 index=2 处截断（取前 3）。
30 秒面试「动态 TopK 不做固定截断：按 Rerank 分数降序后，从最小保留数开始检测相邻分数的断崖（绝对落差 ≥0.5 或相对落差 ≥25%），出现断崖就在那里截断，最多 10 条、至少 1 条。这样低分垃圾文档不会混进 Prompt，答案质量更稳。」

概念 E · 从多路到精排：两段式漏斗

一句话结论「多路召回 → RRF 融合 → Rerank 精排 → 动态截断」构成标准两段式漏斗：召回保覆盖率，排序保精度。 [通用知识]
大白话先广撒网（召回），再精挑细选（排序），最后只把最好的几份资料端上桌（TopK）给大模型。
前端类比像商品列表页：先按类目粗筛出 100 个（召回），再按综合分排序（RRF），再精排推荐算法排序（Rerank），最后只展示前 10 个（TopK）。
项目代码app/query_process/agent/main_graph.py：node_join → node_rrf → node_rerank → node_answer_output 的顺序边。
最小代码
builder.add_edge("node_join", "node_rrf")        # 融合
builder.add_edge("node_rrf", "node_rerank")      # 精排
builder.add_edge("node_rerank", "node_answer_output")  # 生成
为什么这样写：把「召回量」和「精度」两个目标拆到不同阶段，每阶段可独立优化（加一路召回 / 换重排模型）。
反例召回直接进 Prompt：10 路结果全塞进上下文，Token 爆掉、噪音淹没真相关文档，答案质量崩。
并发场景漏斗各阶段是串行依赖（融合需等全部召回），但不同用户的漏斗可并行；瓶颈通常在 Rerank 算力。
边界漏斗的最终输出上限是 10 条：如果知识库里相关文档超过 10 条，后面会被截掉；如果召回本身漏了（召回率不足），再好的排序也救不回来 —— 召回与排序是乘法关系。
验证方法跟踪一个真实问题的 rrf_chunks 数量（应 ≤10）与 reranked_docs 数量（≤10），确认漏斗逐步收敛。
30 秒面试「我把检索设计成两段式漏斗：召回阶段广撒网（向量/HyDE/Web/图谱四路并行），保证覆盖率；排序阶段先用 RRF 按排名融合去重，再用 Rerank 模型精读打分，最后动态 TopK 截断。召回和排序是乘法关系，任何一段短板都会拉低最终答案质量。」

闭卷回答

  1. 写出 RRF 核心公式，并说明 rank、weight、k 各自的含义。
  2. k=60 时第 1 名和第 2 名的得分差大约是多少？说明了什么？

动手任务：手算一次 RRF + 断崖截断

  • 输入：两路 mock 结果 —— 路1（权重1.0）：[A, B, C]；路2（权重1.0）：[B, A, D]，k=60
  • 操作：① 手算 A、B、C、D 的 RRF 分（A：1/61+1/62；B：1/62+1/61；C：1/63；D：1/63）；② 排序并确认 Top3；③ 跑 node_rrf 的本地测试对照
  • 预期结果：A ≈ B 且都 > C=D，融合后 [A/B 或 B/A, C, D]；A、B 因为两路都出现而领先
  • 失败先查：若结果不同，检查 rank 是否从 1 开始（enumerate start=1）

讲一遍「投票（RRF）→ 精读（Rerank）→ 划及格线（动态 TopK）」的漏斗故事，并说明每一级在防什么错。
