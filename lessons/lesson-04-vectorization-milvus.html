3. 概念讲解

概念 A · 主体识别（node_item_name_recognition）：为检索打标签

一句话结论用 LLM 从切片中提取「主体名称」（如商品型号），作为业务标签存进元数据，检索时能按主体过滤和增强。 [项目事实]
大白话一份说明书里可能同时讲了好几个产品。主体识别就像给每块「知识卡片」盖一个章：「这张卡讲的是万用表 RS-12」。盖章后，用户问万用表时就能优先找盖了万用表章的卡。
前端类比像给数据打标签（tagging）/ 给文章加分类。也像前端给路由加 meta 字段（如 requiresAuth），后续中间件按 meta 做鉴权 —— 这里按 item_name 做检索增强。
项目代码app/import_process/agent/nodes/node_item_name_recognition.py；提示词文件 prompts/item_name_recognition.prompt；ImportGraphState 里字段 item_name。
最小代码
# 主体识别：LLM 提取商品名（伪代码）
item_name = llm_invoke_extract(chunk_text)  # "HAK 180 烫金机"
chunk["metadata"]["item_name"] = item_name   # 写进切片元数据
state["item_name"] = item_name               # 存到全局状态
为什么这样写：把「业务知识」从纯文本里显式提出来，检索时可以做字段过滤 + 文本增强（拼接 item_name + 内容一起向量化）。
反例不识别主体：用户问「HAK 180 烫金机怎么操作」时，系统只能靠纯向量相似度碰运气；商品名一旦写法和文档不一致，召回质量不稳定。
并发场景批量文档同时导入：每个文档的 item_name 提取是独立 LLM 调用，可按文档并发；同一文档内保持顺序。
边界LLM 提取有误识别风险（把「烫金机」识别成「烫金」）；所以检索端还有一道「意图确认」关卡（node_item_name_confirm）做二次确认和反问。
验证方法导入文档后打印 state["item_name"]，人工核对与文档真实主题是否一致。
30 秒面试「主体识别是在导入时用 LLM 从每个切片提取商品名等业务标签，写进元数据。它的价值是让检索链路能按主体过滤和做文本增强，并且和检索端的意图确认配合，形成『导入打标 + 检索确认』的闭环，提升命中准确率。」

概念 B · BGE-M3 双向量（稠密 + 稀疏）

一句话结论BGE-M3 同时输出稠密向量（1024 维，记语义）和稀疏向量（变长键值对，记关键词），混合使用兼顾语义与精确匹配。 [项目事实]
大白话稠密向量像「一个人的气质画像」，抽象但全面；稀疏向量像「名片上的关键词列表」，具体但零散。检索时既比气质又对关键词，两个都对上的最相关。
前端类比稠密 ≈ 语义嵌入（embedding 模型给整段文字一个向量）；稀疏 ≈ 倒排索引里的词频（类似搜索引擎的 TF）。两者结合 = 语义搜索 + 关键词搜索同时做。
项目代码app/import_process/agent/nodes/node_bge_embedding.py：单例 get_bge_m3_ef、批量生成 embeddings、文本增强（拼接 item_name + 内容）；工具函数在 app/lm/embedding_utils.py。
最小代码
# 单例模型：全局只加载一次，省显存省时间
def get_bge_m3_ef():
    global _bge_m3_ef
    if _bge_m3_ef is None:
        _bge_m3_ef = FlagModel(model_name_or_path=..., use_fp16=True)
    return _bge_m3_ef

# 双向量生成（伪代码）
embeddings = generate_embeddings([item_name + " " + chunk_text])
chunk["dense_vector"]  = embeddings.dense[0]    # 1024 维列表
chunk["sparse_vector"] = embeddings.sparse[0]   # {token_id: weight}
为什么这样写：单例避免模型重复加载（每个模型几百 MB 到几 GB）；拼接 item_name 强化主体特征，检索更准。
反例只用稠密向量：精确型号「RS-12」这类关键词可能被语义淹没，同义词过多时召回不准。只用稀疏向量：同义表达（「怎么用」vs「如何操作」）匹配不上。双路互补。
并发场景大批量切片向量化：分批处理（batch）防止显存溢出；多 GPU 可并行，但项目以单机单卡为主，靠批次控制内存。
边界向量化是「离线重」步骤：10 万条切片可能耗时数分钟到数十分钟。它发生在导入期而非查询期，所以查询链路依然很快 —— 这就是「以空间/离线算力换在线速度」的典型权衡。
验证方法调用 generate_embeddings 打印 dense 向量长度（应 1024）和 sparse 向量类型（dict）。
30 秒面试「向量化用 BGE-M3 同时生成稠密和稀疏双向量：稠密向量捕捉语义相似度，稀疏向量捕捉关键词精确匹配。模型单例加载、分批处理防显存溢出，并把商品名拼进文本增强主体特征。入库时两个向量都存进 Milvus，检索时做混合打分。」

概念 C · Milvus 集合、Schema 与自动建表

一句话结论Milvus 的集合（Collection）像 MySQL 的表；Schema 定义字段（含向量字段和索引类型），项目在集合不存在时自动创建。 [通用知识] [项目事实]
大白话集合 = 一张「向量表」，每行是一条切片：主键 chunk_id、正文 content、商品名 item_name、稠密向量、稀疏向量。Schema = 建表语句，声明每列是什么类型、向量多少维、用什么索引。
前端类比像定义 TypeScript 接口 + 建 MySQL 表：字段、类型、索引一起声明。自动建表像 ORM 的 auto-migrate，首次连库自动把表建好。
项目代码app/import_process/agent/nodes/node_import_milvus.py step_2_prepare_collection：连接 Milvus、集合不存在则创建 Schema + 索引；配置在 app/conf/milvus_config.py。
最小代码
from pymilvus import DataType
# 集合不存在时自动创建（伪代码）
if not client.has_collection(CHUNKS_COLLECTION_NAME):
    schema = client.create_schema(auto_id=True)          # 主键自增
    schema.add_field("chunk_id", DataType.INT64, is_primary=True)
    schema.add_field("content", DataType.VARCHAR, max_length=8192)
    schema.add_field("item_name", DataType.VARCHAR, max_length=256)
    schema.add_field("dense_vector", DataType.FLOAT_VECTOR, dim=1024)
    schema.add_field("sparse_vector", DataType.SPARSE_FLOAT_VECTOR)
    client.create_collection(CHUNKS_COLLECTION_NAME, schema=schema)
为什么这样写：自动建表让「部署即用」，不用手工初始化；向量维度从上游校验结果取，保证一致。
反例手工建表：换环境/换集合名就要手工执行 SQL，容易漏建索引导致查询极慢；自动建表 + 代码内校验维度，降低运维心智负担。
并发场景两个任务同时发现集合不存在并发创建：Milvus 客户端有幂等处理，但规范上应在主图层面串行初始化（或加锁），避免竞争建表。
边界Schema 一旦创建，字段/维度很难改（要删集合重建）。维度必须和模型输出严格一致（1024），改模型换维度时必须重建集合 —— 这是上线后最痛的迁移点。
验证方法首次导入后查 Milvus 集合列表和字段结构，确认 chunk_id/content/dense_vector/sparse_vector 齐全。
30 秒面试「Milvus 的集合相当于向量表，Schema 声明字段和索引。我们的入库节点在集合不存在时自动建表，向量维度从数据校验结果传入，保证 Schema 与模型输出一致。上线初期用自动建表降低运维成本，但 Schema 一旦定了就很难改，换模型要重建集合。」

概念 D · 幂等导入：先删后插 + 主键回填

一句话结论同一份文档重复导入不会产生重复数据：入库前先删除该 item_name 的旧数据，再批量插入；Milvus 自增 chunk_id 回填到切片供下游使用。 [项目事实]
大白话「幂等」= 同一操作做 100 遍和做 1 遍结果一样。导入场景里，用户改了 PDF 重新导入是常态；先删旧的再插新的，库里永远只有最新版本，不会越导越多。
前端类比像「全量替换」而非「追加」：重新构建时先清空 dist 再打包（clean + build），而不是每次往 dist 里追加文件。
项目代码app/import_process/agent/nodes/node_import_milvus.py：step_3_clean_old_data 按 item_name 删除旧数据；step_4_insert_data 批量插入并把 Milvus 生成的 chunk_id 回填 state["chunks"]。
最小代码
# 幂等：按 item_name 清旧
client.delete(collection_name, expr=f'item_name == "{item_name}"')
# 批量插入，Milvus 返回自增主键
insert_result = client.insert(collection_name, data=rows)
ids = insert_result.primary_keys
# 主键回填：把 chunk_id 写回每个切片，供下游引用
for chunk, cid in zip(chunks, ids):
    chunk["chunk_id"] = cid
state["chunks"] = chunks
为什么这样写：先删后插保证「重导即更新」；回填 chunk_id 让下游（检索返回、历史记录）能定位到具体切片。
反例只插不删：同一文档导入 3 次库里 3 份，检索时重复结果占满 TopK，且旧版本过时内容还会被答出来 —— 数据污染最典型的来源。
并发场景同一文档被两个任务同时导入：先删后插的「删」可能误删对方刚插入的数据。解决方向是导入任务串行化（按 item_name 加锁）或事务隔离 —— 这是幂等设计里最容易翻车的并发细节。
边界「按 item_name 删」要求 item_name 稳定且能唯一定位文档；如果两个不同文档同名（同名不同版本），删除会误伤。真实项目需要引入 document_id/版本号做更细粒度的幂等键。
验证方法同一 PDF 连续导入两次，查 Milvus 里该 item_name 的行数保持不变（而不是翻倍）。
30 秒面试「Milvus 入库节点保证幂等：插入前按 item_name 删除旧数据再批量插入，同一文档重复导入不会产生重复切片；Milvus 自增的 chunk_id 回填给切片，下游可以精确定位。这个『先删后插』策略让重导即更新，避免数据污染。」

概念 E · 数据校验：脏数据不进库

一句话结论入库前逐项校验（chunks 非空、向量字段齐全、维度提取），任一不满足就抛异常终止，宁可失败也不写脏数据。 [项目事实]
大白话像快递入库前先扫码核对：没有收件人（空 chunks）不收货；货物破损（缺向量字段）不收货。宁愿这一单失败，也不让坏货混进仓库污染整个库存。
前端类比像表单提交前的校验（required、格式检查），前端不合格不发请求；也像 TypeScript 在编译期拦截类型错误。
项目代码app/import_process/agent/nodes/node_import_milvus.py step_1_check_input；node_bge_embedding.py 的 step_1_validate_input 同样做前置校验。
最小代码
chunks_json_data = state.get("chunks")
if not chunks_json_data:
    raise ValueError("错误: chunks为空，无法执行Milvus入库")
if not isinstance(chunks_json_data, list) or len(chunks_json_data) == 0:
    raise ValueError("chunks 不是有效列表")
# 校验向量字段存在 + 提取维度
vector_dimension = len(chunks_json_data[0].get("dense_vector", []))
为什么这样写：校验失败 raise 终止节点，由主流程捕获记录，保证「失败可见」，不静默写坏数据。
反例不校验直接插入：空列表插入成功但库无数据、缺向量字段插入直接报 Milvus 类型错误，问题暴露在更深处，排查成本高。
并发场景校验是纯内存操作，无共享状态，天然并发安全。
边界校验能拦「结构错误」但拦不了「内容错误」（如 item_name 识别错了）—— 内容质量靠模型和二次确认兜底，校验只管结构完整性。
验证方法故意传空 chunks 调用节点，观察是否抛出「chunks为空」的 ValueError。
30 秒面试「入库前做严格的数据校验：chunks 必须非空列表、必须有稠密向量字段、提取向量维度。校验失败直接抛异常终止，保证脏数据不进库。结构校验在前，内容质量靠主体识别模型和检索端二次确认兜底。」

4. 课后提取和动手任务

闭卷回答

  1. 稠密向量和稀疏向量各捕捉什么信息？为什么要两个都用？
  2. 主体识别放在向量化之前有什么好处？
  3. 「先删后插」为什么能实现幂等？它的并发风险是什么？
  4. Milvus Schema 里 dense_vector 维度为什么必须与模型一致？改模型维度会怎样？

动手任务：验证幂等导入

  • 输入：一个小 MD 文档 + Milvus 可用环境
  • 操作：① 首次导入，记录 Milvus 中该 item_name 的行数 N1；② 修改文档内容后再次导入；③ 查询行数 N2
  • 预期结果：N1 ≈ N2（而不是翻倍），且内容已是新版本
  • 失败先查：若行数翻倍，检查 step_3_clean_old_data 的删除表达式是否匹配 item_name；若查询报错，检查集合名配置 milvus_config.py
  • 注意：勿在共享生产环境做破坏性验证；用测试集合或本地 Milvus
