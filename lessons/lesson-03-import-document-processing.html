3. 概念讲解

概念 A · node_entry：入口节点的「校验 + 路由」

一句话结论入口节点负责参数校验、按文件后缀设置解析开关、提取业务标识（file_title），本身不解析内容。 [项目事实]
大白话就像快递站收件员：先检查包裹地址（local_file_path 非空）、看是文件还是生鲜（PDF/MD/其他）、贴个标签（file_title），然后交给对应的分拣线。
前端类比类似路由入口的守卫函数：校验 query 参数、判断来源、设置默认值，然后 next() 到对应页面。也像 axios 请求拦截器先校验配置再发请求。
项目代码app/import_process/agent/nodes/node_entry.py：add_running_task 记录开始；state.get("local_file_path") 校验；endswith 判断 .pdf/.md；os.path.basename + splitext 提取 file_title。
最小代码
document_path = state.get("local_file_path", "")
if not document_path:
    logger.error("未配置 local_file_path，文件路径为空")
    return state                      # 缺参：直接返回，流程后续走默认分支
if document_path.endswith(".pdf"):
    state["is_pdf_read_enabled"] = True
    state["pdf_path"] = document_path
elif document_path.endswith(".md"):
    state["is_md_read_enabled"] = True
    state["md_path"] = document_path
file_name = os.path.basename(document_path)
state["file_title"] = splitext(file_name)[0]   # "万用表RS-12的使用.pdf" → "万用表RS-12的使用"
为什么这样写：把「判断」留在入口、把「干活」交给后续节点，职责单一；开关字段驱动条件路由。
反例不做校验直接往下传空路径：后续节点打开不存在的文件直接抛异常，错误堆栈又深又难定位；入口校验能最早暴露问题。
并发场景同时导入 PDF 和 MD：两个 state 各自开关不同，路由函数各走各的分支，互不干扰。
边界入口只认 .pdf/.md 后缀：传一个 .txt 时两个开关都为 False，路由返回 END 静默结束 —— 项目靠日志 warning 提示「不支持的格式」。真机上带扩展名大小写（.PDF）会识别失败。
验证方法运行 `python -m app.import_process.agent.nodes.node_entry`，观察 TXT/MD/PDF 三种测试的日志分支走向。
30 秒面试「导入链路的入口节点做三件事：校验文件路径非空、按后缀把 PDF/MD 路由到不同处理线、提取 file_title 作为业务标识。判断逻辑和业务逻辑分离，后续节点职责单一。」

概念 B · node_pdf_to_md：PDF 转 Markdown

一句话结论PDF 是排版文档，先用专业解析器（MinerU）转成结构化 Markdown，才能被后续切片和向量化处理。 [项目事实]
大白话PDF 像一张「照片」，文字和排版糊在一起，机器直接读容易乱；Markdown 像「源代码」，标题、表格、段落结构清清楚楚。先转格式再加工。
前端类比类似把 Figma 设计稿导出成 HTML/CSS：设计稿（PDF）是给人看的，导出结构（MD）是给机器用的。或像 pdf2htmlEX / pandoc 这类格式转换工具。
项目代码app/import_process/agent/nodes/node_pdf_to_md.py，解析器配置在 app/conf/mineru_config.py。
最小代码
# 伪代码（项目实际用 MinerU 服务）
result = mineru_parse(pdf_path)        # 调用 PDF 解析服务
md_content = result.get("markdown")    # 得到结构化 Markdown
state["md_content"] = md_content
state["md_path"] = output_md_path      # 落盘，供下一节点使用
为什么这样写：专业解析器能识别标题层级、表格、公式，切片时才能按语义切而不是按字符硬切。
反例直接用 pypdf 抽取纯文本：表格散架、标题层级丢失，切片切出「半句话」，向量检索质量断崖式下降。
并发场景a、b 两个 PDF 同时转 MD：解析服务要支持并发或排队，否则会成为导入瓶颈（每个 PDF 可能耗时几十秒到几分钟）。
边界扫描版 PDF（纯图片无文字层）MinerU 也未必能直接转好，通常需要 OCR 环节 —— 项目若遇到扫描件，质量可能不达标，属于已知边界。
验证方法导入一个带标题和表格的 PDF，打开生成的 md_path 文件，检查标题层级和表格是否被正确保留。
30 秒面试「PDF 是排版文档，直接抽文本会丢失标题、表格等结构信息，我用 MinerU 这类专业解析器转成 Markdown，保留语义结构，为后续语义切片打好基础。这是导入链路质量的第一道关口。」

概念 C · node_md_img：图片提取与路径修复

一句话结论把 Markdown 里的图片提取出来上传到 MinIO，并把文档里的图片路径替换为可访问的 URL，保证前端能展示。 [项目事实]
大白话Markdown 里的图片链接常常指向本地文件（比如 `![图1](images/1.png)`），这些路径只有服务器自己认识。图片节点把图片搬到公共网盘（MinIO），再把链接改成网盘地址，这样前端浏览器也能看到图。
前端类比像前端把本地图片上传到 CDN 再引用 CDN 地址，而不是引用 `C:/Users/xxx/1.png`；也像 webpack 的 asset 处理 —— 小图转 base64 / 大图输出到 public 目录并改写引用路径。
项目代码app/import_process/agent/nodes/node_md_img.py；MinIO 配置在 app/conf/minio_config.py；最终答案节点用正则 `_extract_images_from_docs` 从切片文本中提取图片 URL 展示给用户。
最小代码
import re
pattern = re.compile(r'!\[.*?\]\((.*?)\)')   # 匹配 Markdown 图片语法
matches = pattern.findall(md_content)        # 找出所有图片路径
for m in matches:
    url = minio_upload(m)                    # 上传 MinIO，返回公网 URL
    md_content = md_content.replace(m, url)  # 替换路径为 URL
为什么这样写：图片和文本解耦 —— 文本进向量库，图片进对象存储，检索回答时再按需提取图片 URL。
反例不处理图片直接向量化：模型向量化的是「图片路径字符串」而非图片内容，回答时前端也加载不了本地路径的图，功能直接缺失。
并发场景多个文档含大量图片同时导入：MinIO 上传是网络 IO，可能成为瓶颈；通常按文件粒度并发，一个文件内部串行上传。
边界只处理标准 Markdown 图片语法 `![alt](url)`；HTML `` 或其他写法可能漏处理。提取时需防重复（用 seen 集合去重）。
验证方法导入一个含图片的 MD，检查 MinIO 桶里是否多出对应对象、md 文件里的路径是否变成 URL。
30 秒面试「图片节点解决一个实际问题：Markdown 里的图片路径是服务器本地路径，前端访问不了。我把图片提取上传到 MinIO，把路径替换成公网 URL。这样检索回答时能通过正则从文档里提取图片 URL 直接展示给用户，形成图文答案。」

概念 D · node_document_split：文档切片（为什么切 / 怎么切）

一句话结论长文档必须切成小片段才能向量化、检索和放入 Prompt，切片质量直接决定 RAG 检索效果。 [通用知识] [项目事实]
大白话向量模型和 LLM 都有长度限制（Token 上限），而且检索时「一整本书」没法回答「某一页的问题」。切片就是把书拆成「知识点卡片」，每张卡片自带上下文。
前端类比像把一个巨型组件拆成多个可复用的小组件；也像虚拟列表只渲染可视区域。切片大小类似「组件粒度」：太大复用难、太小碎片多。
项目代码app/import_process/agent/nodes/node_document_split.py；ImportGraphState 里有一组切片策略开关：is_normal_split_enabled、is_silicon_flow_api_enabled、is_advanced_split_enabled、is_vllm_enabled。
最小代码
# 策略选择示意（项目支持多种切片引擎，通过开关路由）
chunks = []
if state.get("is_normal_split_enabled"):
    chunks = normal_split(md_content)          # 基础按段落/字符切
if state.get("is_silicon_flow_api_enabled"):
    chunks = silicon_flow_api_split(md_content)  # 云端 API 语义切
if state.get("is_advanced_split_enabled"):
    chunks = advanced_split(md_content)        # 高级语义切分
state["chunks"] = chunks   # 每块含 text + metadata（如标题、页码）
为什么这样写：不同文档适合不同切法，把策略做成开关，业务可按需启用，不影响链路骨架。
反例不切片整篇向量化：① 超出模型长度直接报错；② 检索命中整个文档，Prompt 撑爆上下文；③ 相似度被长文本稀释，相关性下降。
并发场景切片是纯计算/API 调用，可按文档并行；同一个文档内的切片顺序要保持（metadata 里带索引），便于后续按序组装上下文。
边界切片不是越小越好：过小会切断语义（一句话被劈两半），过大又稀释相关性。同时 chunk 应尽量「自带上下文」（如保留小标题），否则检索到一块孤立的「50℃」不知道在说什么。
验证方法导入长文档后，打印 chunks 数量和每块长度；抽查一块是否完整包含一个语义单元（如一个操作步骤）。
30 秒面试「文档切片是 RAG 的基石。受限于模型长度和检索精度，我把长文档切成带上下文的语义片段，每个片段包含文本和元数据。项目支持基础切分、云端 API 语义切分、高级切分多种策略，通过状态开关选择，切片质量直接影响后续检索和生成质量。」

4. 课后提取和动手任务

闭卷回答

  1. node_entry 里 `.pdf` 后缀判断失败会怎样？哪个字段决定后续分支？
  2. PDF 直接抽文本相比用 MinerU 转 MD，丢失了什么？
  3. 图片节点解决了什么「前端视角」的问题？
  4. 切片太大会有什么后果？太小呢？

动手任务：验证一次真实导入

  • 输入：一个测试 PDF 或 MD（可用 doc/ 下现成文档）
  • 操作：① 看 node_entry.py 单元测试怎么构造 state；② 照样子构造初始 state（task_id、local_file_path）invoke 导入主图；③ 打印中间状态里的 file_title、md_path、chunks 数量
  • 预期结果：日志显示完整的 7 节点链路走向，chunks 数量 > 0
  • 失败先查：若卡在 PDF 转 MD，先确认 MinerU 服务/配置（mineru_config.py）是否可用；若 chunks 为空，检查切片开关默认值
  • 注意：首次运行可能依赖环境变量，先确认 .env 齐全；不要导入大文件，用小 PDF 验证

口述复盘

用「收件员 → 格式转换 → 搬家到网盘 → 拆卡片」的比喻，讲一遍文档从 PDF 到可检索切片的完整旅程。
