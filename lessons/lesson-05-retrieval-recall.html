3. 概念讲解

概念 A · 意图确认：听懂用户问的是哪个商品

一句话结论先用 LLM 从问题+历史中提取商品名并改写问题，再用向量检索到商品库核对置信度，按规则确认或反问/拒绝。 [项目事实]
大白话用户说「这个多少钱？」——「这个」指什么？系统先结合上一轮历史推断出商品名，再去商品库里查这个商品是不是真的存在，置信度高就直接往下查，模糊就给用户几个选项确认，查不到就老实说没有。
前端类比像前端路由的「参数解析 + 鉴权」：先从 URL 解析出参数（LLM 提取 item_names），再校验参数是否合法（Milvus 查证），不合法就 400 让用户改（反问/拒绝）。
项目代码app/query_process/agent/nodes/node_item_name_confirm.py：step_3_extract_info（LLM 提取 item_names + rewritten_query）→ step_4_vectorize_and_query（向量化+Milvus 商品库搜索）→ step_5_align_item_names（评分规则 A-D）→ step_6_check_confirmation（更新状态）。
最小代码
# 评分规则（节选）
high = [m for m in matches if m.get("score", 0) > 0.85]  # 高置信
mid  = [m for m in matches if m.get("score", 0) >= 0.6]  # 中置信
if len(high) == 1:        # 规则A：唯一高置信 → 确认
    confirmed_item_names.append(high[0]["item_name"])
elif len(high) > 1:       # 规则B：多个高置信 → 同名优先/取最高
    ...
elif len(mid) > 0:        # 规则C：只有中置信 → 进候选，反问用户
    options.extend(mid)
else:                     # 规则D：低分 → 拒绝回答
为什么这样写：分数阈值把「确定」「模糊」「不存在」三类情况分开处理，避免系统自作主张答错商品。
反例不确认直接检索正文：用户问「华为 P60」时库里同时有 128G 和 Art 两个型号，系统可能拿错型号的说明书来回答，答非所问。
并发场景a 问烫金机、b 问万用表：各自提取各自的 item_names，各自查商品库，评分互不影响；确认结果各自写进自己的 state。
边界规则依赖阈值（0.85/0.6），阈值不是万能的：极端情况「库里有 5 个相似型号都 >0.85」会走规则 B 取最高分，仍可能选错 —— 所以候选反问（规则 C）比硬猜更安全。
验证方法构造 4 种 mock 评分（唯一高/多高/中/低），单测 node_item_name_confirm 看走哪个分支，日志有「规则A/B/C/D命中」字样。
30 秒面试「意图确认是检索前的『听懂』环节：先用 LLM 从问题和历史中提取商品名、改写独立完整的问题，再向量检索商品库核对置信度。0.85 以上唯一就确认，多个就取同名或最高分，0.6 左右进候选反问用户，太低就拒绝。这一步保证后续检索永远基于『确认过的商品』，避免答错型号。」

概念 B · 问题改写（rewritten_query）

一句话结论把「不完整的口语问题」结合历史改写成「独立完整的问题」，让后续向量检索和 LLM 都能正确理解。 [项目事实]
大白话用户第一句「HAK 180 怎么操作？」，第二句「那温度设多少？」—— 第二句单独看不知道在说什么。改写把它变成「HAK 180 烫金机的温度应该设置多少？」，独立成句。
前端类比像搜索引擎的 query 补全 / 会话式搜索的上下文注入；也像把「它」这种代词在代码里替换成真实变量名，消除歧义。
项目代码app/query_process/agent/nodes/node_item_name_confirm.py step_3_extract_info；提示词 prompts/rewritten_query_and_itemnames.prompt；QueryGraphState 字段 rewritten_query。
最小代码
# LLM 提取（JSON 结构化输出）
result = json.loads(llm_response)   # {"item_names": [...], "rewritten_query": "..."}
state["item_names"] = result.get("item_names", [])
state["rewritten_query"] = result.get("rewritten_query", query)
为什么这样写：检索和生成都用 rewritten_query，而不是用户原话，避免「这个」「那个」这类代词破坏向量相似度。
反例直接用原始问题向量化：「这个多少钱」向量化后和任何商品文档都不相似，召回全空。
并发场景每个会话的历史不同，改写出不同结果；session_id 隔离保证互不串扰。
边界改写依赖 LLM：模型可能改写错误或漏掉关键信息（尤其多轮历史很长时），所以项目同时保留 original_query 作为兜底，prompt 里 `question = rewritten_query if rewritten_query else original_query`。
验证方法模拟两轮对话，观察 state["rewritten_query"] 是否把「那温度设多少」补全为含商品名的完整问句。
30 秒面试「多轮对话里用户常问『这个多少钱』这种不完整问题，直接向量化根本匹配不上。我在意图确认阶段用 LLM 结合历史把问题改写成语义完整的 rewritten_query，后续检索、Rerank、生成全部基于改写后的问题，准确率明显提升。」

概念 C · 四路并行召回：向量 / HyDE / Web / 图谱

一句话结论同一问题同时走「稠密+稀疏混合检索、HyDE 假设文档检索、联网搜索、知识图谱检索」四路，再汇合排序，提高召回覆盖率。 [项目事实]
大白话单路检索像只问一个朋友；四路检索像同时问四个擅长不同方面的朋友，最后综合意见。每个朋友都可能发现别人没注意到的线索。
前端类比像「多数据源聚合」：前端同时请求本地缓存、远程 API、CDN、第三方服务，然后合并展示 —— 并行请求 + 结果聚合。
项目代码app/query_process/agent/main_graph.py：node_multi_search 分叉到 node_search_embedding / node_search_embedding_hyde / node_web_search_mcp / node_query_kg，全部汇入 node_join。
最小代码
# 四路各自的产出（都进 node_join）
state["embedding_chunks"]      # 向量混合检索：本地知识库切片
state["hyde_embedding_chunks"] # HyDE：先假设答案再检索的切片
state["web_search_docs"]       # Web 搜索：实时/库外信息
state["kg_chunks"]             # 图谱检索：实体关系信息
为什么这样写：知识库覆盖不到的实时信息（如最新价格）靠 Web 路，语义模糊的表达靠 HyDE 路，精确型号靠向量路 —— 互补覆盖。
反例只有向量一路：用户问「这机器现在多少钱」（需要实时信息，库里有历史文档但没最新价格）时答不出；或用户表达方式与文档完全不同时召回失败。
并发场景四路是并行执行的，总耗时 ≈ 最慢一路。若 Web 搜索超时（MCP 服务 300 秒超时），会拖慢整个回答 —— 所以各节点必须降级返回空列表，不能让单路故障阻塞全链路。
边界多路召回是「召回阶段」的策略，召回多了必然混入噪音 —— 这正是后续 RRF + Rerank 存在的意义：先把多路结果融合去重，再精排筛掉无关项。
验证方法观察检索日志中四路各自返回的数量：embedding/hyde 一般非空，web 在有实时需求时非空，kg 视图谱数据而定。
30 秒面试「召回阶段我做了四路并行：向量混合检索覆盖本地知识库的语义匹配，HyDE 先让 LLM 生成假设答案再检索来弥合表达差异，Web 搜索补充实时和库外信息，知识图谱提供实体关系。四路结果汇合后交给 RRF 融合去重、Rerank 精排。多路召回提升覆盖率，后续排序负责去噪。」

概念 D · HyDE（假设性文档嵌入）

一句话结论HyDE = 先让 LLM 根据问题写一段「假设答案」，再用这段答案去向量检索 —— 因为答案和文档更相似。 [通用知识] [项目事实]
大白话问题「这机器怎么用」和文档「操作说明」风格差异大，向量距离远。HyDE 让 LLM 先假装回答「操作步骤是……」，生成的假设答案和文档风格接近，检索命中率提高。
前端类比像搜索前先「用 AI 生成一个理想答案片段」作为搜索关键词，再拿它去搜 —— 类似「以文搜文」而非「以词搜文」。
项目代码app/query_process/agent/nodes/node_search_embedding_hyde.py；提示词 prompts/hyde_prompt.prompt。
最小代码
# HyDE：先生成假设文档（伪代码）
hypo_doc = llm.invoke(hyde_prompt.format(query=rewritten_query))
embeddings = generate_embeddings([hypo_doc])     # 用假设文档向量化
results = hybrid_search(client, collection, ...)  # 检索知识库
state["hyde_embedding_chunks"] = results
为什么这样写：把「问题→文档」的检索转化为「文档→文档」的检索，弥合 query 与 doc 的表示鸿沟。
反例不用 HyDE：用户口语化提问（「咋整」「咋弄」）与文档书面语差距大，纯向量检索相似度低，TopK 里可能全是无关文档。
并发场景HyDE 和普通向量检索并行：HyDE 多一次 LLM 调用（多几百毫秒~几秒），但和主路并行，不增加总时延。
边界HyDE 假设答案可能「编造细节」，检索会偏向相似风格的文档 —— 它提升召回但不提升精度，噪音需要 Rerank 消除。且多一次 LLM 调用增加成本。
验证方法对比同一问题普通检索与 HyDE 检索的 Top5 chunk_id 差异，观察 HyDE 是否召回更多语义相关的文档。
30 秒面试「HyDE 的核心是让 LLM 先根据问题生成一段假设答案，再用这段答案做向量检索。因为假设答案和知识库文档的表示更接近，能弥合口语问题与书面文档之间的语义鸿沟，提升召回率。它和普通向量检索并行执行，不增加总时延，但会带来噪音，交给后面的 Rerank 精排消除。」

概念 E · Web 搜索 MCP：把外部世界接进来

一句话结论通过 MCP（Model Context Protocol）连接远程 Web 搜索工具，给知识库补充实时和库外信息。 [项目事实]
大白话知识库是「公司的档案柜」，Web 搜索是「上网查」。档案柜里没有的（比如昨天刚发布的新型号价格），上网一查就有。MCP 就是「统一插头」，让 AI 应用能即插即用各种外部工具。
前端类比像前端调用第三方 API（天气、地图、支付）——通过统一 SDK 接入；MCP 相当于 AI 领域的「统一 API 协议」，SSE 是它的传输通道之一。
项目代码app/query_process/agent/nodes/node_web_search_mcp.py：MCPServerSse 连接百炼 WebSearch 服务；配置 app/conf/bailian_mcp_config.py；调用工具 bailian_web_search。
最小代码
search_mcp = MCPServerSse(name="search_mcp", params={
    "url": mcp_config.mcp_base_url,
    "headers": {"Authorization": mcp_config.api_key},
    "timeout": 300, "sse_read_timeout": 300})
await search_mcp.connect()                     # 建立 SSE 连接
result = await search_mcp.call_tool("bailian_web_search", {"query": rewritten_query})
state["web_search_docs"] = parse_result(result)
为什么这样写：用现成 MCP 工具而非自建爬虫，鉴权、重试、协议都由 MCP 服务端封装。
反例只依赖知识库：用户问「现在最新款是什么」这类时效性问题，文档库永远滞后，答案过时甚至没有。
并发场景多个会话同时触发 Web 搜索：MCP 客户端是每请求新建连接，注意连接数上限；超时 300 秒的设置是为慢搜索兜底，实际大部分秒级返回。
边界Web 搜索结果是「未经验证的第三方信息」，可信度低于本地知识库 —— 所以 Rerank 阶段把 local 和 web 合并打分，但 prompt 里标注来源（[local]/[web]），让 LLM 和用户都能区分。
验证方法问一个知识库里没有但网上常见的时效性问题（如某型号最新价格），观察 web_search_docs 是否有返回，答案是否引用了 web 来源。
30 秒面试「知识库解决『公司内部文档』，但覆盖不了实时和外部信息。我用 MCP 协议连接百炼 Web 搜索工具，作为第四路召回：MCP 统一了工具接入方式，SSE 传输，鉴权超时都有封装。搜索结果是未经验证的外部信息，所以重排后会在答案里标注 [local]/[web] 来源。」

4. 课后提取和动手任务

闭卷回答

  1. 意图确认的评分规则 A/B/C/D 分别对应什么场景？
  2. 为什么「这个多少钱」必须改写成独立完整问题才能检索？
  3. 四路召回各自弥补了什么盲区？
  4. HyDE 提升的是召回率还是精度？为什么？

动手任务：mock 四路召回并观察 RRF 输入

  • 输入：node_item_name_confirm.py 的单元测试部分（`__main__`）
  • 操作：① 运行该节点单测，观察 step_3/4/5/6 日志走向；② 记录最终 state 的 confirmed_item_names 和 options；③ 手动构造三种输入（唯一高/多个高/中置信），看规则分支日志
  • 预期结果：日志出现「规则A/B/C/D命中」，确认结果符合预期
  • 失败先查：若连不上 Milvus，检查 .env 的 Milvus 配置；若 LLM 提取失败，检查提示词文件与 API Key
  • 注意：涉及外部依赖（LLM/Milvus），首次运行确保环境就绪；可先只看日志不看真实检索
