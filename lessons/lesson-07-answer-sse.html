3. 概念讲解

概念 A · 答案节点主流程（5 个阶段）

一句话结论答案节点按「查答案 → 组 Prompt → 生成 → 写历史 → 发 final」五步走，是检索链路的终点。 [项目事实]
大白话先看有没有现成答案（比如意图确认阶段的反问句），有就直接发；没有就备好 Prompt、调大模型生成、把答案存进历史、最后通知前端「完事了，可以渲染图片了」。
前端类比像前端页面渲染前先查缓存：缓存命中直接渲染，未命中则请求接口 → 拿到数据 → 写 store → 通知订阅者更新。
项目代码app/query_process/agent/nodes/node_answer_output.py：step_1_check_answer → step_2_construct_prompt → step_3_generate_response → step_4_write_history → final push。
最小代码
answer_exists = step_1_check_answer(state)
if not answer_exists:
    prompt = step_2_construct_prompt(state)
    state["prompt"] = prompt
    step_3_generate_response(state, prompt)
image_urls = _extract_images_from_docs(state.get("reranked_docs") or [])
if state.get("answer"):
    step_4_write_history(state, image_urls=image_urls)
if state.get("is_stream"):
    push_to_session(session_id, SSEEvent.FINAL,
                    {"answer": state["answer"], "status": "completed",
                     "image_urls": image_urls})
为什么这样写：把「判断/组装/生成/持久化/推送」拆成独立步骤，任一阶段可单独测试与降级。
反例不检查已有答案直接生成：意图确认阶段的反问句会被当成「用户的真实回答」重新生成一遍，多花钱还答错。
并发场景多个会话同时走到答案节点：各自独立生成、独立写历史、独立推送；MongoDB 写入按 session_id 区分。
边界写历史失败不应阻塞主链路（项目用 try/except 包住 save_chat_message，失败只记日志）；final 推送只发生在流式模式。
验证方法跑节点本地测试，观察日志中五个阶段的顺序与「写入MongoDB历史记录」「发送 final 事件」字样。
30 秒面试「答案节点分五步：先检查 state 里是否已有答案（意图确认阶段的反问/拒绝会直接命中），没有就组装 Prompt、调用 LLM 生成（支持流式）、把答案写入 MongoDB 历史，最后推 final 事件并附带图片 URL，触发前端渲染。每一步独立可测，写历史失败不影响主链路。」

概念 B · Prompt 组装与上下文预算

一句话结论把重排文档、历史对话、商品名按格式拼进模板，并用 MAX_CONTEXT_CHARS=12000 统一限长，防止 Token 溢出。 [项目事实]
大白话给大模型「备菜」：从排好序的文档里挑菜（每条带编号、来源、得分、标题标签），一边挑一边算字数，超了预算就停；历史对话同样参与预算分配，防止把大模型「撑死」。
前端类比像模板字符串渲染 + 长度限制：把数据格式化成带元数据的文本块；也像请求体大小限制（如 body 上限 10MB），超限截断。
项目代码app/query_process/agent/nodes/node_answer_output.py step_2_construct_prompt；模板 prompts/answer_out.prompt（含【参考内容】【历史对话】【相关商品/实体】【用户问题】占位符）。
最小代码
docs, used = [], 0
for i, doc in enumerate(reranked_docs, start=1):
    text = (doc.get("text") or "").strip()
    meta = f"[{i}] [{source}] [chunk_id={chunk_id}] [score={score:.4f}] [title={title}]"
    block = meta + "\n" + text
    if used + len(block) > MAX_CONTEXT_CHARS:   # 预算控制
        break
    docs.append(block)
    used += len(block) + 2
context_str = "\n\n".join(docs) if docs else "无参考内容"
为什么这样写：给每条文档带「溯源标签」（第几条/来源/得分/标题），大模型引用时能说清出处；预算共享避免单方面撑爆。
反例不限长直接拼接：文档多时 Prompt 超出模型上下文窗口，调用直接报错；或历史记录挤占文档空间，参考内容被截断，答案质量崩。
并发场景预算按「每个请求自己的状态」计算，互不共享；但要注意全局并发时 LLM 服务的限流。
边界12000 是字符数不是 token 数，不同语言 token 密度不同（中文约 1 字≈1 token）—— 字符预算偏保守安全；极端长历史时历史可能被完全截断（used 已满）。（[待验证] 可按模型实际窗口调优）
验证方法构造超长 reranked_docs + 历史，观察 context_str 长度被限制在 ~12000 内，且文档优先、历史次之被截断。
30 秒面试「答案生成前先组装 Prompt：把重排文档按『编号+来源+得分+标题』格式化成带溯源标签的文本块，和格式化后的历史对话、商品名一起填进模板。全程用 MAX_CONTEXT_CHARS=12000 统一限长，文档优先、历史次之，防止超出模型上下文窗口。」

概念 C · SSE 流式输出

一句话结论SSE（Server-Sent Events）通过 session_id 队列把 LLM 生成的增量逐字推给前端，事件类型：ready / progress / delta / final / error。 [项目事实]
大白话大模型像打字员一个字一个字地「说」，SSE 像广播台：每说一个字就广播一次，前端收到一个字渲染一个字，用户看到答案「打出来」的效果，而不是干等十几秒。
前端类比前端用 EventSource 建立 SSE 连接，监听事件流；和 WebSocket 的区别是 SSE 单向（服务端→客户端）、自动重连、基于 HTTP，适合「推送答案」这种场景。
项目代码app/utils/sse_utils.py：SSEEvent 常量、_session_stream 队列字典、push_to_session、sse_generator；节点里 llm.stream() 每个增量 push delta。
最小代码
class SSEEvent:
    READY="ready"; PROGRESS="progress"; DELTA="delta"
    FINAL="final"; ERROR="error"; CLOSE="__close__"

# 服务端：流式生成中逐字推送
if is_stream:
    for chunk in llm.stream(prompt):
        delta = getattr(chunk, "content", "") or ""
        if delta:
            push_to_session(session_id, SSEEvent.DELTA, {"delta": delta})
# 前端：EventSource 监听
const es = new EventSource(`/api/chat/stream?session_id=${sid}`);
es.addEventListener("delta", e => appendText(JSON.parse(e.data).delta));
es.addEventListener("final", e => renderImages(JSON.parse(e.data).image_urls));
为什么这样写：会话队列（session_id → Queue）天然隔离多用户；SSE 格式 `event: xxx\ndata: json\n\n` 由 _sse_pack 统一打包。
反例不用流式，等 LLM 全部生成完再返回：十几秒的空白等待，前端只能转圈，体验差；超长答案还可能触发网关超时。
并发场景a、b 两个用户同时提问：各自 session_id 对应各自队列，push 按 session 路由，互不串流；队列消费由各自的 SSE 生成器完成。
边界SSE 单向推送，前端不能通过它发消息（发消息走普通 POST）；连接断开时队列无人消费可能堆积 —— 项目有 remove_sse_queue 清理。LLM 流式异常时推 error 事件告知前端。
验证方法浏览器打开流式接口，用 DevTools Network 观察 SSE 事件流，逐个出现 ready → progress → delta×N → final。
30 秒面试「答案流式输出用 SSE 实现：FastAPI 端维护 session_id → Queue 的映射，LLM 流式生成时每个增量都 push 到该会话队列，sse_generator 把队列内容按 `event: xxx` 格式推给前端 EventSource。事件分 ready/progress/delta/final/error。相比 WebSocket，SSE 单向、基于 HTTP、自动重连，正合适做『服务端→客户端』的答案推送。」

概念 D · 图片「双保险」提取

一句话结论最终展示的图片 URL 不是 LLM 生成的，而是代码从源文档里用正则提取的 —— 因为大模型不可控、源数据最准。 [项目事实]
大白话Prompt 里让大模型输出【图片】区块，只是让它「在文字里提到图」；真正给前端渲染的图片，是代码自己去排好序的文档里扒出来的真实存在的图片链接。双保险：一个引导、一个兜底。
前端类比像前端不信任用户输入，最终渲染前用 schema 校验/白名单过滤一遍；也像「服务端返回数据 → 前端再 sanitize」的双保险。
项目代码app/query_process/agent/nodes/node_answer_output.py _extract_images_from_docs：正则 `!\[.*?\]\((.*?)\)` 匹配 Markdown 图片 + 检查 url 字段后缀（png/jpg/jpeg/gif/webp/bmp/svg）+ seen 去重。
最小代码
md_img_pattern = re.compile(r'!\[.*?\]\((.*?)\)')
for doc in docs:
    url = (doc.get("url") or "").strip()
    if url.lower().endswith(('.png','.jpg','.jpeg','.gif','.webp','.bmp','.svg')):
        if url not in seen: images.append(url); seen.add(url)
    for m in md_img_pattern.findall(doc.get("text") or ""):
        if m not in seen: images.append(m); seen.add(m)
为什么这样写：LLM 可能编造 URL 或格式错误；从源文档提取保证「这图真的存在于参考内容里」。
反例直接解析 LLM 生成的【图片】区块：模型可能给出一个不存在的 URL，前端展示裂图，用户看到的是「坏掉的图」。
并发场景图片提取是纯正则内存操作，无共享状态，并发安全。
边界只认标准 Markdown 图片语法与常见图片后缀；文档里用 HTML `` 或非常见后缀（如 .avif）会漏提取 —— 属于已知边界，可扩展正则。
验证方法本地测试 mock 含 `![图](http://.../panel.jpg)` 的文档，检查提取结果是否只包含真实 URL 且无重复。
30 秒面试「图片展示用了双保险：Prompt 里要求 LLM 输出【图片】区块是为了让文字能提到图，但最终给前端渲染的 URL 是代码用正则从排好序的源文档里提取的真实图片链接（Markdown 语法 + url 字段后缀校验 + 去重）。因为大模型不可控、源数据最准，前端永远只拿到真实存在的图。」

概念 E · MongoDB 历史写入

一句话结论把本轮问答（角色、答案、商品名、图片）写入 MongoDB，供多轮对话上下文与历史查询使用。 [项目事实]
大白话每次问答都「记账」：谁问了什么、AI 答了什么、涉及哪些商品、附了哪些图。下次用户说「这个多少钱」时，系统翻历史账本才知道「这个」指什么。
前端类比像把聊天记录存到 localStorage/数据库，刷新页面还能接着聊；也像埋点/操作日志，可回溯。
项目代码app/clients/mongo_history_utils.py：save_chat_message、get_recent_messages、update_message_item_names；节点里 step_4_write_history 调用 save_chat_message(session_id, role="assistant", text=answer, item_names, image_urls)。
最小代码
def step_4_write_history(state, image_urls=None):
    if state.get("answer"):
        save_chat_message(
            session_id=state["session_id"],
            role="assistant",
            text=state["answer"],
            rewritten_query="",
            item_names=state.get("item_names") or [],
            image_urls=image_urls,
            message_id=None)
    return state  # 写失败也不中断（异常被捕获记日志）
为什么这样写：历史是「多轮对话的记忆」；失败降级保证答案已经生成完毕，不因记账失败丢失。
反例不存历史：多轮对话中「那温度呢」永远无法关联到上一轮的「HAK 180 烫金机」，意图确认阶段提取商品名失败。
并发场景并发写入 MongoDB 由数据库自身保证；同一会话的消息按时间有序写入，读取时按时间排序还原上下文。
边界历史无限增长会让 get_recent_messages 越来越慢 —— 项目通常只取最近 N 条作为上下文，不是全量历史。长会话的截断策略是 [待验证] 的优化点。
验证方法完成一轮问答后查 MongoDB 对应 session 的文档，确认 role/text/item_names/image_urls 字段已落库。
30 秒面试「问答结束后把本轮答案、商品名、图片 URL 写入 MongoDB，作为多轮对话的记忆。下次提问时意图确认节点会读取最近历史，结合上下文提取商品名和改写问题。写历史失败会降级——只记日志不中断主链路，因为答案已经生成了。」
